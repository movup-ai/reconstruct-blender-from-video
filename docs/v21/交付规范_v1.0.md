# 白模素材交付规范

版本 1.0 · 2026-11-06 生效

本规范适用于所有白模素材交付。核心变化：**交付包只上传到 R2，多维表格只记录元数据和对比视频**，不再在表格里挂最终打包文件。

## 0. 总览

一个镜头就是一个**包**。每个包有一个永久唯一的包名，每提交一次就是该包的一个**版本**（v1、v2…）。

```
制作完成
  -> 按第 2 节打 zip
  -> 运行 check_package.py 自检，通过后生成 .zip.sha256
  -> 按第 3 节上传到 R2 的版本目录
  -> 上传本批次新一版 manifest_v{n}.csv（每次修改版本号加 1）
  -> 在多维表格登记元数据、挂对比视频
  -> 我方验收、审核
```

## 1. 包名

- 格式为 `{片名}-{序号}`，只能使用**小写字母、数字、下划线 `_`、连字符 `-`**。片名中的单词用下划线连接。

  | 正确 | 错误 | 原因 |
  | --- | --- | --- |
  | `the_greatest_showman-1` | `The Greatest Showman-1` | 有大写和空格 |
  | `a_fistful_of_dollars-1` | `the_greatest_showman-1_手杖登场_最终交付` | 有中文和多余后缀 |
  | `kill_bill_volume_1-3` | `kill_bill_volume_1-3.final` | 有多余后缀 |

- **包名在全部批次、全部团队内永久唯一，序号不能复用。** 同一部片子分几批交付，序号要接着往后编，不能每批都从 1 开始。此前出现过两批都用 `forrest_gump-1` 到 `-15` 的情况：两个不同的镜头用了同一个包名，结果互相覆盖。
- 返修沿用原来的包名，只升级版本号（见第 3 节）。

## 2. 压缩包

### 2.1 格式

- **只接受 `.zip`**，不接受 `.rar`、`.7z`、`.tar.gz`。
- 文件名就是包名：`{包名}.zip`。

### 2.2 路径分隔符：不能出现反斜杠

zip 内的所有路径必须用正斜杠 `/` 分隔，**不能出现反斜杠 `\`**。

用反斜杠打的包在 Windows 上看起来正常，但在 Linux 和 macOS 上解压后目录结构会全部丢失：每个文件都变成根目录下一个带 `\` 的长文件名，例如 `forrest_gump-1\comparison\comparison.mp4`。此前有 443 个包因此返工。

| 工具 | 是否可用 |
| --- | --- |
| 7-Zip（右键 -> 7-Zip -> 添加到压缩包，格式选 zip） | 可用 |
| PowerShell 7 及以上的 `Compress-Archive` | 可用 |
| Python `zipfile` / `shutil.make_archive` | 可用 |
| **Windows PowerShell 5.1 的 `Compress-Archive`**（Windows 10/11 自带的那个） | **不可用，会产生反斜杠** |
| 其他工具 | 打完后用自检脚本检查 |

### 2.3 目录结构

zip 根目录直接放内容，**不要外面再套一层 `{包名}/` 目录**：

```
the_greatest_showman-1.zip
├── comparison/
│   └── comparison.mp4              必需：对比视频
├── target/
│   └── original.mp4                必需：原片
├── white_model/
│   └── blendervid.mp4              必需：白模渲染
├── model_3d/
│   ├── the_greatest_showman-1.blend    必需：文件名与包名一致
│   ├── the_greatest_showman-1_material.blend
│   └── reconstruction/
│       ├── scene.json              必需
│       └── ……
└── meta/
    ├── meta.json                   必需
    └── ……
```

### 2.4 内容要求

- **路径**：上面标为必需的文件，路径和文件名必须与示例完全一致，只能用英文字母、数字、`_`、`-`、`.`。
- **中文文件名**：`meta/` 下的说明文档等其他文件可以用中文命名，但 zip 必须以 UTF-8 记录文件名。7-Zip、PowerShell 7、Python 默认就是这样；用别的工具打包后，以自检脚本的结果为准。
- **空格**：所有路径都**不能有空格**。
- **嵌套压缩包**：zip 里不能再放 `.zip`、`.rar`、`.7z`。
- **系统垃圾文件**：不能有 `__MACOSX/`、`.DS_Store`、`Thumbs.db`、`desktop.ini`。
- **视频**：所有 mp4 都必须能完整播放。宽度为 1920，高度为 1080 的整数倍（1920x1080，或上下拼接的 1920x2160）。分辨率不符的不会退回，但会被标记出来，并通知你们。
- **Blender 文件**：`.blend` 必须是 Blender 正常保存的文件（未压缩、gzip 或 zstd 压缩均可）。
- **对比视频一致**：zip 内的 `comparison/comparison.mp4` 必须和单独上传的 `comparison.mp4`、多维表格里挂的对比视频是**同一个文件**（逐字节相同）。三者不一致，说明交付的包和审核看到的视频不是同一次产出，这个版本会被直接退回。

## 3. R2 目录与版本

每家供应商使用独立的 R2 桶，凭证由我方发放，只对自己的桶有写权限。下文中的桶名统一写作 `{vendor_bucket}`。

```
r2://{vendor_bucket}/raw/
└── batch20261104/                            首次提交日期（北京时间）
    ├── manifest_v1.csv                       本批次汇总文件（第 4 节），首次提交时生成
    ├── manifest_v2.csv                       每次修改都新建下一版，旧版保留
    ├── the_greatest_showman-1/
    │   ├── v1/                               首次提交
    │   │   ├── comparison.mp4
    │   │   ├── the_greatest_showman-1.zip
    │   │   └── the_greatest_showman-1.zip.sha256
    │   └── v2/                               第一次返修
    │       ├── comparison.mp4
    │       ├── the_greatest_showman-1.zip
    │       └── the_greatest_showman-1.zip.sha256
    └── the_greatest_showman-2/
        └── v1/
            └── ……
```

### 3.1 规则

- **批次目录** `batch{YYYYMMDD}`：用包**首次提交**那天的日期（北京时间）。当天首次提交的包都放在当天的批次目录里。
- **返修不换批次**：返修版本仍然放在原批次的原包目录下，新建 `v{n+1}/`。例如 11 月 4 日首次提交、11 月 6 日返修，返修版本放在 `batch20261104/{包名}/v2/`，**不放**在 `batch20261106/` 下。
- **版本只增不改**：已经上传的 `v{n}/` 不能覆盖、不能删除。哪怕只改了一个文件，也要新建下一个版本目录。版本号只用 `v1`、`v2`、`v3`……，不要用 `v1.1`、`v2_fix`、`final`。
- **每个版本目录只放三个文件，文件名固定**：

  | 文件 | 说明 |
  | --- | --- |
  | `comparison.mp4` | 对比视频，与 zip 内的 `comparison/comparison.mp4` 是同一个文件 |
  | `{包名}.zip` | 交付包 |
  | `{包名}.zip.sha256` | 交付包的校验文件 |

### 3.2 校验文件 `{包名}.zip.sha256`

标准 `sha256sum` 格式，只有一行：64 位小写十六进制哈希、两个空格、zip 文件名。

```
2f14397f8c0d4e9b5a6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8f9012345  the_greatest_showman-1.zip
```

- 推荐直接用自检脚本生成：所有检查都通过时，脚本会自动在 zip 旁边写出这个文件。
- 手工生成时，在 Linux/macOS 上运行 `sha256sum the_greatest_showman-1.zip > the_greatest_showman-1.zip.sha256`。在 Windows 上，PowerShell 里运行 `(Get-FileHash the_greatest_showman-1.zip).Hash.ToLower()`（或者 `certutil -hashfile the_greatest_showman-1.zip SHA256`）得到哈希，然后按上面的格式写入（注意是两个空格）。手工写入容易出错，Windows 上更推荐用自检脚本生成。
- 验证：在 Linux/macOS 的版本目录下运行 `sha256sum -c the_greatest_showman-1.zip.sha256`，输出 `OK` 即可；在 Windows 上，用 `Get-FileHash` 算出的哈希和文件里的比对。

### 3.3 上传顺序

1. `{包名}.zip`
2. `comparison.mp4`
3. `{包名}.zip.sha256`：最后上传，表示这个版本的文件已经传齐
4. 上传本批次新一版的 `manifest_v{n+1}.csv`（第 4 节）
5. 更新多维表格（第 5 节）

我方以本批次**版本号最大的** manifest 里列出的版本为准。版本目录里文件不齐，或者最新 manifest 里没有列出的版本，视为还没有交付完成。

## 4. 汇总文件 `manifest_v{n}.csv`

每个批次目录下维护一组汇总文件：`raw/batch{YYYYMMDD}/manifest_v1.csv`、`manifest_v2.csv`……模板见同目录的 `manifest_template.csv`。

### 4.1 版本规则

- 批次首次提交时上传 `manifest_v1.csv`。
- **之后每修改一次，版本号加 1**，上传为新文件 `manifest_v{n+1}.csv`。触发修改的情况包括：本批次有包返修、补交了新的包、修正了某一行的内容。
- **旧版 manifest 不能覆盖、不能删除**，和包的版本目录一样只增不改。这样每次改动前后的状态都能追溯。
- 每一版都是**完整清单**：列出本批次的全部包，每个包写它当时的最新版本。不要只写这次改动的那几行。
- 版本号连续递增，从 `v1` 开始，不能跳号或重复。一次上传多个包的返修时，只升一个版本号，把所有改动写进同一版 manifest 里。

例如：11 月 4 日首次提交 30 个包，生成 `manifest_v1.csv`。11 月 6 日其中 2 个包返修到 v2，就复制 `manifest_v1.csv`，改掉这 2 行的版本、哈希、大小和时间，另存为 `manifest_v2.csv` 上传。

### 4.2 格式

- UTF-8 编码（带不带 BOM 都可以）；第一行是表头，表头必须和模板一致；之后每个包一行。
- 用 Excel 编辑时，保存时“文件类型”要选 **“CSV UTF-8（逗号分隔）”**。不要选普通的“CSV（逗号分隔）”，那样会存成 GBK 编码，中文到我方会变成乱码。模板本身就是 UTF-8 带 BOM，Excel 直接打开不会乱码。
- Excel 可能把哈希、大小这类长数字显示成科学计数法，保存后数值就坏了。保存前确认这几列是完整的原文；也可以改用记事本或 VS Code 编辑。
- 每个包一行，写它在这一版 manifest 生成时的最新版本。

| 列 | 说明 | 示例 |
| --- | --- | --- |
| `package_name` | 包名 | `the_greatest_showman-1` |
| `version` | 当前版本 | `v2` |
| `zip_sha256` | zip 的 sha256，与 `.zip.sha256` 中的哈希相同 | 64 位小写十六进制 |
| `zip_size` | zip 的字节数 | `40912345` |
| `comparison_sha256` | `comparison.mp4` 的 sha256 | 64 位小写十六进制 |
| `movie_title` | 电影名称，与多维表格一致 | `马戏之王` |
| `theme` | 选片题材，与多维表格一致 | `手杖登场` |
| `lens` | 镜头，取值见附录 | `标准/中焦镜头` |
| `num_characters` | 角色数量，取值见附录 | `三人以上` |
| `camera_movement` | 拍摄运镜，多个用 `; ` 分隔，取值见附录 | `跟拍; 固定镜头` |
| `submitted_at` | 当前版本的上传时间，ISO 8601 格式，带时区 | `2026-11-06T14:00:00+08:00` |

`zip_sha256`、`zip_size`、`comparison_sha256` 必须和 R2 上的文件完全一致，我方用它们做到货核对。自检脚本会直接输出这三项。

## 5. 多维表格

多维表格只记录**元数据和对比视频**，方便审核人员在表格里直接预览。**`最终打包文件` 字段不再使用**，交付包只通过 R2 交付。每个包一条记录。

### 5.1 字段

| 字段 | 谁填 | 说明 |
| --- | --- | --- |
| `包名` | 供应商 | 与 R2 上的包名一致 |
| `批次` | 供应商 | 如 `batch20261104` |
| `当前版本` | 供应商 | 如 `v2` |
| `R2 路径` | 供应商 | 当前版本目录，如 `raw/batch20261104/the_greatest_showman-1/v2/` |
| `zip sha256` | 供应商 | 与 `.zip.sha256` 中的哈希相同 |
| `对比视频 sha256` | 供应商 | 与 manifest 中的 `comparison_sha256` 相同 |
| `电影名称`、`选片题材`、`镜头`、`角色数量`、`拍摄运镜` | 供应商 | 与现在的填法相同 |
| `白模对比视频` | 供应商 | v1 的 `comparison.mp4` |
| `返修对比视频` | 供应商 | 最新返修版本的 `comparison.mp4`，每次返修都替换成新的 |
| `最终打包文件` | —— | **不再使用，留空** |
| `审核状态`、`审核意见`、`审核意见附件`、`返修结果` | 我方 | 供应商不修改，返修时清空 `返修结果`的情况除外（见 5.3） |

### 5.2 首次提交

1. 按第 3.3 节把 v1 传到 R2，并上传本批次的 manifest（批次第一次提交为 `manifest_v1.csv`）。
2. 新建记录：填写包名、批次、`当前版本 = v1`、R2 路径、两个 sha256 和描述字段，在 `白模对比视频` 挂上 v1 的 `comparison.mp4`。
3. `审核状态` 留空，表示待审。

### 5.3 返修

1. 审核结果为 `审核状态 = 返修`，或者 `返修结果 = 继续修改` 时，按 `审核意见` 修改。
2. 按第 3.3 节把新版本传到 R2 的 `v{n+1}/`，然后上传这个包所在批次的下一版 manifest（例如原来最新是 `manifest_v1.csv`，就上传 `manifest_v2.csv`）。
3. 更新同一条记录：`当前版本`、`R2 路径`、两个 sha256；在 `返修对比视频` 换上新版本的 `comparison.mp4`；**清空 `返修结果`**，表示待复审。

**一定要先传 R2，再改表格。** 顺序反过来的话，审核人员看到了新视频，R2 上却还没有对应的包。

## 6. 自检与验收

### 6.1 上传前自检

每个版本上传前运行同目录的 `check_package.py`。需要 Python 3.9 或以上，不用装其他依赖。Windows、Linux、macOS 都可以运行。

先把三个文件放进本地的版本目录，和 R2 上的结构一致：`{包名}.zip`、`comparison.mp4`；`.zip.sha256` 由脚本生成。然后任选一种方式运行：

| 系统 | 方式 |
| --- | --- |
| Windows（最简单） | 把版本目录拖到 `check_package.bat` 上，窗口里会显示结果 |
| Windows 命令行 | `py check_package.py D:\交付\the_greatest_showman-1\v1` |
| Linux / macOS | `python3 check_package.py ./the_greatest_showman-1/v1` |

也可以分别指定两个文件：`py check_package.py the_greatest_showman-1.zip comparison.mp4`。

Windows 上请从 [python.org](https://www.python.org/downloads/) 安装 Python（安装时勾选 “Add python.exe to PATH”）。`check_package.bat` 会优先使用 `py` 启动器，避免误调用 Microsoft Store 里的占位程序。

- 脚本逐项检查第 1、2 节的规则，并打印每一项的结果。
- **全部通过**：在 zip 旁边生成 `the_greatest_showman-1.zip.sha256`，并打印 manifest 需要的 `zip_sha256`、`zip_size`、`comparison_sha256`。
- **有任何一项不通过**：退出码不为 0，**不会**生成 `.zip.sha256`。改好以后重新打包，再跑一次自检。

自检只检查文件结构，视频能否完整解码由我方验收时检查。

### 6.2 我方验收

到货后，我方用同一套规则复核，并逐项核对：

- R2 上 zip 的 sha256 与 `.zip.sha256`、最新版 manifest、多维表格三处记录一致；
- 本批次的 manifest 版本号从 `v1` 起连续，没有缺号；
- 多维表格里的对比视频、R2 上的 `comparison.mp4`、zip 内的 `comparison/comparison.mp4` 三者一致；
- 所有视频能完整解码，分辨率符合要求。

不通过的版本不进入审核，原因写在多维表格的 `审核意见` 里。修好后以**下一个版本号**重新上传，不要覆盖原来的版本。

## 7. 常见问题

| 问题 | 后果 | 怎么避免 |
| --- | --- | --- |
| 用 Windows 自带的 PowerShell 5.1 打包，路径里有 `\` | 目录结构丢失，整包返工 | 用 7-Zip 或 PowerShell 7；跑自检 |
| 新一批又从序号 1 开始编 | 与已有的包同名，互相覆盖 | 序号接着往后编 |
| zip 外面套了一层 `{包名}/` 目录 | 结构不符 | 选中目录里的内容来打包，不要选目录本身 |
| 交 `.rar` | 不接收 | 只交 `.zip` |
| 覆盖了已经上传的版本 | 审核记录与文件对不上 | 任何修改都新建 `v{n+1}/` |
| 覆盖了旧的 manifest，或者新版 manifest 只写了改动的几行 | 无法追溯，我方会漏收 | 每次修改上传 `manifest_v{n+1}.csv`，内容是完整清单 |
| 表格里的对比视频和 zip 里的不是同一个 | 直接退回 | 三处用同一个 `comparison.mp4`；跑自检 |

## 附录：取值

与多维表格的选项一致，**只能用下列取值**。

- **镜头**：`广角镜头`、`鱼眼镜头`、`标准/中焦镜头`、`长焦镜头`
- **角色数量**：`单人`、`双人`、`三人`、`三人以上`
- **拍摄运镜**（可多选）：`推镜头`、`拉镜头`、`摇镜头`、`移镜头`、`跟拍`、`环绕`、`升降`、`手持纪实`、`滚转镜头`、`无人机穿越`、`希区柯克镜头`、`固定镜头`
